# 1.0.7：不打开 App 时的自动提醒

用户已明确：不是要求自动展开卡片，而是“不打开今天课程 App，就没有流体云”。本次集中处理后台唤醒权限和可独立复核的后台链路，不以手动预览或 onResume 补发作为成功证据。

## 权限路径

原版在没有 `SCHEDULE_EXACT_ALARM` 授权时退回非精确闹钟。非精确闹钟可能被延迟，打开 App 又会根据当前课表补发通知，因此仅凭“打开后有提醒”无法确定手机究竟有没有收到原闹钟。

课程日历的核心功能需要准时提醒。根据 [Android 官方闹钟文档](https://developer.android.com/develop/background-work/services/alarms/schedule)，Android 13 及以上改用自动授予的 `USE_EXACT_ALARM`；`SCHEDULE_EXACT_ALARM` 限制到 API 32，供 Android 12 / 12L 用户授权。仍以实际 `canScheduleExactAlarms()` 结果为准，不能因为清单声明权限就声称当前系统已允许。普通提醒保留受限时的回退，后台自测则在没有精确权限时明确拒绝安排，避免产生误导结果。

这解决精确权限路径的缺口，尚不能据此证明该 OPPO 上的全部故障已解决。ColorOS 自启动、后台活动、一键清理、通知提升和强行停止策略仍需手机验证。

## 一分钟后台自测

在「我的 → 提醒设置 → 后台提醒」点击「1 分钟后自动测试」，立刻回到桌面，4 分钟内不要打开 App 或点即时预览。

| 点击测试后的时间 | 预期行为 |
| --- | --- |
| 1 分钟 | 自动发布“后台自动提醒测试”，计时指向第 2 分钟 |
| 2 分钟 | 切换课中计时，指向第 4 分钟 |
| 3 分钟 | 发布独立“快下课”提示 |
| 4 分钟 | 清理测试通知 |

测试直接复用生产环境的 `CoursePlanner`、关键时点队列、`AlarmManager` 的 `PendingIntent`、清单接收器与系统 Live Updates 通知。临时课程独立保存在原生偏好中，不写入 Drift 数据库、不改动真实课表、不自动打开 Activity 或启动 Flutter。无需真实课程，也可在普通提醒开关关闭时显式测试。

仅收到带正确计划时间的生产闹钟广播，才允许显示测试课程。手动刷新/重新打开 App 不会解锁首次显示，因而不能再以打开后的补发伪装后台测试成功。回调次数、实际到达时间、原计划时间与通知提交结果分别记录；未收到回调与收到但发布失败会显示不同结果。“已提交通知”仍不等于 ColorOS 实际显示了流体云。

临近真实课程或正在预览时拒绝启动测试；后续新加入的真实课程也始终优先。用户可取消整个测试；测试通知自身的关闭动作沿用普通/下课独立关闭规则。不会取消真实课程的系统闹钟。重启可从持久化配置恢复队列；完成后的临时测试不会循环或复活。

## 结果判断

- 未收到后台回调：检查 ColorOS 的自启动/后台活动/一键清理策略；锁定后台后再测。强行停止会撤销系统闹钟，需用户重新打开才能恢复。
- 已收到回调，通知提交失败：检查本应用及通知分类权限。
- 已收到回调并提交通知，桌面却没有流体云：继续检查实时通知提升权限、系统选择和展示策略。这与 App 没有被系统唤起不同。

## 验证范围

通过 flutter analyze、89 项 Flutter 测试、98 项 Kotlin/Robolectric 测试、ARM64 release 构建与 Android lint（无 Error/Fatal）。安装包已核对 1.0.7（18）、原开发签名、16 KB 对齐，以及 `USE_EXACT_ALARM` / `SCHEDULE_EXACT_ALARM maxSdkVersion=32` 的实际打包声明。

原生框架测试沿生产 PendingIntent 依次送达四个时点，不创建 Flutter 页面、不调用即时预览；覆盖 Android 36 / 37，以及手动打开不能伪造回调、取消后保留真实课程闹钟、重启恢复、拒绝无权限测试、通知发布失败单独记录、临近真实课程拒绝测试。Flutter 测试覆盖安排/取消桥接、等待状态及三种不同提交结果。

云环境未连接 OPPO 手机。这些测试证明应用内部的状态与系统 API 调用，没有实测 ColorOS 的清理行为、自动授权结果或岛的实际展示。本版本应通过上述四分钟流程取得手机证据。
