# 清理后台后的提醒：1.0.5

## 报告和边界

用户报告在 OPPO / ColorOS 上清理后台后流体云消失，且需重新打开应用才显示上课、下课提醒。当前没有连接该手机，不能从现象断定是厂商清理策略、强行停止、准时提醒权限还是其他系统限制。

原实现已使用清单注册的 BroadcastReceiver、持久化课表与 AlarmManager PendingIntent，没有在 Activity 销毁时主动取消提醒。普通进程回收按 Android 的机制不应撤销这些闹钟。但原先只安排下一次关键闹钟，依靠回调继续安排后续提醒；如果前一回调没有到达，后续下课或下一门课的闹钟可能尚未登记。打开 App 的 onResume 刷新会补发当前提醒，容易掩盖这个区别。

## 本次改动

- 课前、上课、下课前、下课的时点去重排序，提前向系统登记最近 64 个独立唤醒闹钟；正常触发后补足队列。上课时点也独立安排，避免缺少课前回调时只能等到下课提示。单个时点丢失不再阻断其余已登记时点。
- 每个时点有唯一、不可变的 PendingIntent。新队列先登记，再取消失效时点。修改提前量、删除课程、关闭提醒都会清理相应旧闹钟。旧版单闹钟自动迁移。
- 系统闹钟回调只读取原生 SharedPreferences，无需 Flutter 页面或 Activity 存活。重启、升级、时区/时间变更继续通过原有恢复广播重建队列。
- 多个延迟闹钟一起到达时，相同卡片不重复提交，避免新提示被立即静默覆盖；升级时仍会清除旧通知中导致倒计时冻结的静态短文本。
- 预览撤下时点和真实课表共用有界队列；分钟外观刷新仍使用不唤醒设备的 RTC，并避开关键边界。系统 Chronometer 倒计时保持不变。
- 新增后台限制、电池优化状态、已登记时点数量、下一次唤醒和最近实际后台回调记录。手动打开应用、页面刷新或补发通知不会写入“最近后台触发”。到达时间和原计划时间分别保存，便于发现延迟。
- 提醒设置提供应用信息、电池优化入口，提示 OPPO 用户允许后台活动、自启动（若提供）及锁定后台。使用公开 Settings Intent，页面不可用时回退到应用信息；不会修改用户的系统权限，也不依赖私有保活接口。

## 真机核对

1. 覆盖安装后打开一次，进入「我的 → 提醒设置」，确认通知、顶部实时提醒和准时提醒已允许。
2. 打开后台运行设置，在 ColorOS 的应用耗电/电池管理中允许后台活动和自启动（若提供）；按需在电池优化设置中将本应用设为不优化，并在最近任务里锁定。具体菜单名称随系统版本变化。
3. 添加一门几分钟后开始、稍后结束的测试课程，设置课前、下课前的提前量。退出到桌面后不再打开 App，分别观察两个提醒时点。再按之前的清理方法测试，区分普通退出、单独划走与一键清理。
4. 测试结束后查看“最近后台触发”。如果仍是旧时间，表示没有收到新的系统闹钟回调；如果有回调但未上岛，再检查通知、实时提醒和厂商展示策略。“已提交系统”仅表示通知提交成功，不能证明岛已显示。

Android 强行停止会撤销闹钟和通知，并让应用处于 stopped 状态，通常需用户重新打开才能恢复；有些厂商清理也可能施加类似限制。提前登记队列不能绕过这一机制。电池优化豁免和系统报告“未限制”也不等同于已获得全部 ColorOS 自启动/后台权限。没有准时提醒权限时仍回退到非精确闹钟，可能延迟；系统空闲配额也会影响过于密集的唤醒。

64 个是有限的前瞻队列，不是无限期保证：如果所有回调都被系统拦截，就无法补足后续队列。没有常驻前台服务、无声播放、循环重启或唤醒锁保活。

## 验证

本版本通过 flutter analyze、84 项 Flutter 测试、82 项 Kotlin/Robolectric 测试及 Android lint（无 Error/Fatal）。ARM64 release 构建、包名/版本/原签名与 16 KB 对齐检查通过。

- 原生框架测试：直接跳过全部课前回调，在原先已登记的下课时点通过清单接收器发布提示；覆盖 Android 36 / 37。下一门课同样可以独立触发。
- 测试覆盖：迟到回调的计划/到达时间、手动打开不能伪造后台记录、修改/删除/关闭的闹钟清理、重启后队列重建、大量导入的 64 个边界上限与续排、分钟刷新不覆盖新提醒。
- Flutter 测试验证后台状态、说明、两个系统设置入口，同时保留已有 UI、导入、手势、数据及提醒测试。
- 上述是框架与应用测试，没有模拟 ColorOS 一键清理或真实强行停止后的系统行为。OPPO 流体云是否持续显示、后台白名单是否生效，仍需上述真机步骤核对。
